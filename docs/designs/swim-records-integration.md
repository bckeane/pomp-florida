## Problem Statement

The Pomperaug Panthers swim & dive program runs two separate sites: `pompFlorida` (this repo — the annual Florida trip site: public landing page, parent registration, admin roster/budget) and `swim.ctkeane.com` (a standalone Vite/React SPA showing the team's all-time swim records — Record Board, Top-20-per-event detail, Swimmer Search, and a Top-25 Excel/PDF export tool). They look and feel like two unrelated products even though they're the same team. The user wants the records/stats site folded into pompFlorida as one cohesive site. A second folder, `adminFrontend` (a CRUD tool for entering swim times), is explicitly deferred — future enhancement only, not touched in this design.

## What Makes This Cool

Right now a parent bookmarking the trip site and a parent bookmarking the records site have no idea they're the same program. Making the records board feel like a native pompFlorida page — same Panther maroon, same footer-link pattern, same polish — turns two disconnected side projects into one real team site.

## Constraints

- The `swim.ctkeane.com` frontend source (what's being ported) is confirmed accessible at `/Users/brian/code/prod/swim-data-app/swim.ctkeane.com` — already inspected in full during this design session (4 components: `RecordBoardContainer`/`RecordBoard`, `Top20`/`Top20List`, `SwimmerSearch`, `Top25Export`). Not a blocker.
- No application-code or route changes on `api.ctkeane.com` (the external backend) — it's read-only from pompFlorida's side, and its current source isn't available in this repo anyway (only a stale, superseded zip, `backend-movedtoMOF.zip`, with entirely different routes than the live API). The live API must be treated as a black box, verified by live probes, not assumed. The one exception, tracked separately as a config/ops step rather than code: the CORS allowlist addition described below (not an application change, and not something this repo's codebase touches).
- **Swimmer Search has no dedicated search endpoint.** The existing implementation has none to inherit — it fetches `/swim/records` for the event list, then loops a client-side `GET /swim/top20/:eventId` call per event and filters results by name in the browser (an N+1 fan-out, not a single query). The port inherits this same client-side-filter pattern; it is a known, accepted cost, not an oversight.
- `adminFrontend` is out of scope for this session.
- pompFlorida has an established design-token system (`--brand-red`, `--brand-red-bright`, a named spacing scale, dark-mode via `prefers-color-scheme`) shared across `home.css`/`register.css`/`faq.css`. New UI must reuse these tokens, not Bulma or new hardcoded colors.
- pompFlorida's client has no persistent navbar — every page is self-contained with its own header and footer links (e.g. HomePage's footer already links to `/faq`, `/register`, `/admin`, `/privacy`). New routes follow that same pattern.
- pompFlorida's API client convention is a plain `fetch` wrapper per resource in `client/src/api/*.js` (no axios anywhere in the codebase).

## Premises

1. All 4 pages (Record Board, Top-20 detail, Swimmer Search, Top-25 Export) ship this pass, as new routes inside pompFlorida's existing client SPA — not a separate deploy, not an iframe — restyled with pompFlorida's existing design tokens.
2. Client fetches `api.ctkeane.com/swim/*` directly from the browser — no new pompFlorida server code.
3. `adminFrontend` stays fully out of scope.
4. Read-only: pompFlorida never writes swim data anywhere.
5. Entry point is a public link from the HomePage footer, no login required (matches swim.ctkeane.com's current no-auth access).

**Finding that revised premise 2's risk profile (live probe, not assumed):** `api.ctkeane.com` runs an origin allowlist, not open CORS. `Origin: https://swim.ctkeane.com` and `Origin: http://localhost:5173` both return clean `200`s with `access-control-allow-origin` echoed back. Any other Origin — tested with pompFlorida's real prod origin (`https://pompflorida-api.onrender.com`, confirmed from this repo's own README) and with an unrelated domain — returns a bare `500 Internal Server Error` (Express default error page), not a graceful CORS rejection. Requests with no Origin header at all (plain curl, or a Node server-side fetch) get `200` fine. Confirmed on both `/swim/records` and `/swim/top20/:id` (the middleware is global, not per-route, so all 4 pages share the same exposure). The user confirmed they control that allowlist and can add pompFlorida's production origin to it before launch. Local dev works today with no changes (`localhost:5173` is already allowlisted).

## Approaches Considered

### Approach A: Straight port
All 4 pages restyled and ported with one shared fetch wrapper, no special failure-state design beyond what swim.ctkeane.com already has (`{error && <p>{error}</p>}`). Fastest, but inherits the original site's fragility — a CORS misconfig or API outage shows a raw, unstyled error with no graceful recovery path.

### Approach B: Straight port + hardened fetch + release checklist — CHOSEN
Same 4 pages, same scope. The shared `client/src/api/records.js` wrapper renders a real "Records temporarily unavailable" state (reusing pompFlorida's existing `.banner--error` pattern already used on HomePage's own error branch) instead of a bare error string. Adding pompFlorida's production origin to `api.ctkeane.com`'s CORS allowlist becomes an explicit release-blocker checklist item, verified with a live curl probe post-deploy — mirroring this repo's existing pattern for Stripe/Resend setup dependencies (documented in `TODOS.md`/`deploy.md`, not just remembered).

**On the cross-model's suggestion to punt Top-25 Export to a follow-up pass:** considered and not taken. The user explicitly chose to keep full 4-page scope in this pass (confirmed when selecting Approach B) — the hardened-fetch-wrapper mitigation applies to all 4 pages equally, not just Export, and Export's specific bundle-weight cost is addressed directly instead (see Next Steps: dynamic import / route-level code-splitting), rather than by deferring the page.

### Approach C: B + roster cross-link (stretch, not built this pass)
Everything in B, plus a best-effort badge on Swimmer Search results when a name matches a current pompFlorida roster participant. Genuinely new value (the cross-model's top suggestion), but real scope: name-matching is fuzzy (common names, nicknames) and needs its own small design pass before it's safe to ship. Captured as a Next Step, not started.

## Recommended Approach

**Approach B.** It delivers everything the user asked for (all 4 pages, this session) while fixing the one real risk two independent checks (the live CORS probe and the cross-model review) both surfaced: a third-party dependency that fails hard instead of degrading gracefully, with no checklist forcing the allowlist step to actually happen before launch. Approach C's idea is real but adds a second axis of risk (data matching quality) that deserves its own pass rather than riding along with a UI port.

## Success Criteria

- All 4 pages render live data from `api.ctkeane.com` inside pompFlorida's own visual shell (Panther maroon, existing spacing/typography tokens), reachable from a "Team Records" link in the HomePage footer, no separate deploy or iframe.
- Each page's fetch has 3 explicit states — `loading` / `success` / `error` — with `error` rendering the styled "temporarily unavailable" banner, not a raw error string or blank page. No fixed timeout is introduced; `error` fires on the fetch's own rejection/non-2xx response (matching pompFlorida's existing `fetchCurrentTrip` error-handling pattern in `HomePage.jsx`), not a race against a clock.
- All 4 pages manually verified against live `api.ctkeane.com` data (not just happy-path assumption) before the footer link ships.
- pompFlorida's production origin (`https://pompflorida-api.onrender.com`) is confirmed live on `api.ctkeane.com`'s CORS allowlist via a post-deploy curl probe — against both `/swim/records` and `/swim/top20/:id` — before the footer link is enabled in production.
- No new pompFlorida server code; no writes to swim data from pompFlorida at any point.

## Eng Review Additions (2026-08-24, /plan-eng-review)

Four changes approved during eng review, on top of the Next Steps above:

1. **Session cache in `records.js`.** Cache each successful response (records list + per-event top20) in-memory/sessionStorage for the tab's lifetime — no invalidation logic needed since swim records only change ~once a season. Protects `api.ctkeane.com` from redundant load as pompFlorida's own traffic grows, and cuts repeat fetches on Search/Export.
2. **Shared `useRecords(url)` hook** (`client/src/hooks/useRecords.js`) instead of each of the 4 pages hand-rolling its own `loading`/`success`/`error` state trio — the source app already has this exact duplication (only `Top20.jsx` uses its `useFetch.js` hook; the other 3 pages don't). Extract the state-machine transitions into a pure `recordsReducer(state, action)` function separate from the hook's `useEffect` wiring, so the branching logic is unit-testable with plain vitest — no RTL needed, consistent with this repo's existing pure-function-only test convention.
3. **Parallelize the per-event fetch loops** in Swimmer Search and Top-25 Export. The source app awaits each event's fetch sequentially inside a `for` loop (`SwimmerSearch.jsx` ~line 1097, `Top25Export.jsx` ~line 405) — with 10-30 events that's 10-30x the latency of doing them at once. Use `Promise.allSettled(events.map(...))` instead; this also naturally produces the fulfilled/rejected split needed for change 4.
4. **"Results/export may be incomplete" notice** on both Swimmer Search and Top-25 Export. Both pages silently swallow a per-event fetch failure in the source (`catch (err) { console.warn(...) }`, no user-visible signal) — a transient failure on one event makes an incomplete result look complete. Track failed-event count from the `Promise.allSettled` results (change 3) and show a small inline notice when `0 < failedCount < total`; when `failedCount === total`, escalate to the full "temporarily unavailable" error banner instead (a total outage deserves the same clear signal as everywhere else on these pages).
5. **Error boundary on all 4 pages, not just Export.** Originally scoped to just the lazy Export chunk-load failure, widened during the Outside Voice pass: a malformed/changed response shape from `api.ctkeane.com` (a black box outside this repo's control) could throw during render on any of the 4 pages, and `useRecords`'s `loading`/`success`/`error` states don't catch render-time exceptions, only fetch-time failures. One shared error boundary component, applied around each page's route (or the whole `/records` subtree), with a "something went wrong, try again" fallback — actually achieves the plan's own stated goal that all 4 pages degrade consistently.
6. **Port-fidelity check on the release checklist.** Outside Voice finding: general manual QA checks "does it render," not "does it render the *same answer* as the source." Top-25 Export is coach-facing and may be acted on directly (season banquet, records recognition) — added as an explicit release-checklist line: before shipping, compare pompFlorida's `/records` and `/records/top25-export` output against `swim.ctkeane.com`'s current live output for the same data (same rankings, same order, same formatted times), not just "it renders without crashing."

**Outside Voice tension resolved, not silently accepted:** the outside voice also challenged Premise 2 itself — arguing a server-side proxy would eliminate the CORS allowlist dependency, the bare-500 failure mode, and the release-blocker checklist entirely, since server-to-server requests never send an Origin header. Re-litigated explicitly (this is the third time direct-fetch vs. proxy was weighed, now with the full cost of hardening itemized) — the user kept direct-fetch. Rationale: the marginal cost of direct-fetch over proxy is really just the CORS allowlist config step, which the user already controls and confirmed twice; a proxy would still need its own graceful-failure handling for when `api.ctkeane.com` itself is down, so most of the hardening work isn't actually proxy-vs-direct-specific. Also considered and rejected: capping fetch concurrency against a theoretical (unconfirmed, no evidence) rate-limit risk from the `Promise.allSettled` parallelization — the user judged this speculative engineering against a service they run and can observe directly.

## Failure modes

| Codepath | Realistic failure | Test coverage | Error handling | User sees |
|---|---|---|---|---|
| `records.js` fetch | `api.ctkeane.com` down, DNS fail, timeout | Unit test (mocked fetch reject) | Yes — `useRecords` catches, sets `error` state | Styled "temporarily unavailable" banner |
| `records.js` fetch | CORS allowlist missing pompFlorida's origin (bare 500) | Unit test (mocked 500 response) + manual release-checklist probe | Yes — same `error` state path (fetch rejects on non-2xx) | Same banner — indistinguishable from a real outage to the end user, which is correct (nothing they can do either way) |
| `useRecords` reducer | Rapid URL change (e.g. clicking two events fast) before first fetch resolves | Unit test (reducer transition test) | Yes — `AbortController` pattern carried over from `useFetch.js` precedent | Sees the second event's data, not a stale/wrong first response |
| Search/Export per-event loop | One event's fetch fails, others succeed | Unit test (`Promise.allSettled` aggregation) | Yes — new "may be incomplete" notice (this review) | Explicit notice instead of a silently wrong complete-looking answer — **this was a critical gap before this review** (no test, no error handling, silent failure) |
| Search/Export per-event loop | ALL events fail (e.g. mid-outage) | Covered by the same aggregation path — `failedCount === total` | Yes | "Results may be incomplete" for all — arguably should be the full error banner instead of a notice at 100% failure; **not resolved, flagged as an open question below** |
| Top-25 Export lazy chunk | The lazy-loaded JS chunk itself fails to fetch (flaky network on first visit to that route) | Not covered — no test planned | Yes — error boundary (Eng Review Additions #5, widened during Outside Voice pass to cover all 4 pages) | Graceful "something went wrong, try again" fallback instead of an uncaught React error / blank section |
| Any of the 4 pages | `api.ctkeane.com` returns a 2xx with an unexpected/changed response shape (missing field, renamed key — it's a black box outside this repo's control) | Not covered — no test planned | Yes — the same error boundary from #5 catches the render-time exception | Graceful fallback instead of a crashed/blank page (Outside Voice finding) |

**Resolved during this review:** at 100% per-event failure (`failedCount === total`), Search/Export escalate to the full "temporarily unavailable" error banner instead of the softer partial-failure notice — a total outage deserves the same clear signal as anywhere else on these pages, not an undersold "may be incomplete" caption on a 0-of-N result.

## Worktree Parallelization Strategy

| Step | Modules touched | Depends on |
|------|-----------------|------------|
| Foundation: `records.js` + `useRecords` hook + `recordsReducer` + session cache | `client/src/api/`, `client/src/hooks/` | — |
| Record Board page | `client/src/RecordsPage.jsx` (or equivalent) | Foundation |
| Top-20 detail page | `client/src/Top20Page.jsx` | Foundation |
| Swimmer Search page (incl. `Promise.allSettled` aggregation + partial-failure notice) | `client/src/SwimmerSearchPage.jsx` | Foundation |
| Top-25 Export page (incl. lazy-load, error boundary, `xlsx`/`jspdf` integration) | `client/src/Top25ExportPage.jsx`, `client/package.json` | Foundation |
| Wiring: routes + footer link | `client/src/App.jsx`, `client/src/HomePage.jsx` | All 4 pages built |
| Release checklist: CORS allowlist verification + manual QA | (ops, no files) | Wiring merged, deployed |

**Execution order:** Build the Foundation lane first (single lane, sequential — everything else depends on it).
